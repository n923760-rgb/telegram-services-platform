# Telegram Services UX v1: bilingual customer experience

Date: 2026-10-07. Task branch: ai/task-20261007-004611.
Starting HEAD: unchanged (no commits made). This round makes the customer experience bilingual
(Arabic default, English opt-in) using the existing `User.language` column with no schema changes,
no migrations, and no service-plugin changes.

## Scope

Localize every bot-authored customer-facing message (menus, intake prompts, confirmations, status,
support flow, and delivery envelopes) and show localized service names via `Service.name_ar` /
`Service.name_en`. Users switch language at runtime through `/lang` or the new main-menu
"language" item; the choice persists per user via the existing `User.language` column.

  No commits, no staging, no pushes, merges, releases, secret changes, or remote mutations.
- No migrations were created; `app/core/models.py` and `app/core/settings.py` were not modified.

## Changed files

1. `app/core/users.py` (new): `get_language(user_id)` (read-only, resolves to `ar` on unknown user
   or transient DB failure; never creates a row) and `set_language(user_id, lang)` (validates
   ar/en, creates the user row only if missing, else updates `language`).
2. `app/bot/middleware.py`: added `UserContext` middleware that resolves the update's
   `from_user.id` language once per update and exposes it as `data["lang"]`. `PrivateChatGate` and
   `Guard` are unchanged.
3. `app/bot/main.py`: imports and registers `UserContext` between `PrivateChatGate` and `Guard`
   (outermost-first ordering preserved).
4. `app/bot/handlers.py`: threaded `lang` through every customer/admin-facing `tr(...)` call;
   added `menu:language` / `/lang` / `lang:` language switch; localized service names; preserved
   all existing draft-recovery, cancel, confirm, intake and admin behavior.
5. `app/bot/ops_handlers.py`: threaded `lang` through the support flow and admin ops. The
   admin-facing `support_context` (and its inner `none`) and `/report` output stay in default
   Arabic (operator text). `reply` resolves the ticket owner's language via `get_language` before
   sending `support_reply`.
6. `app/providers/delivery.py`: `TelegramDelivery` gains a `_lang` helper and localizes `send`,
   `error` and `confirmation` (`result_header`, `structure_preview`, `order_failed`,
   `approve_structure`, `cancel_order`, `confirmation_waiting`). UTF-16 chunk-splitting and artifact
   sending are unchanged; the first `send_message` remains `result_header`.
7. `app/i18n/ar.json` / `app/i18n/en.json`: added `language`, `choose_language`, `language_set`
   (reusing existing `arabic` / `english` labels for the switch buttons).
8. `tests/test_ux.py` (new): three regression tests covering an English user's localized menu and
   service names, runtime language switching that persists and localizes the balance view, and the
   unknown-user Arabic default without user-row creation.
9. `ENGINEERING/MASTER_ROADMAP.md`: appended a FACT bullet to "Current verified state".

## Residual risks

- `get_language` performs one DB read per update when `UserContext` runs; accepted for correctness
  and consistent with existing per-update DB access in `Guard`.
- The bilingual path was verified only by static review; aiogram middleware/FSM routing and the
  delivery envelope localization are not executed here.
- English service names come from the registry-synced `name_en`; there is intentionally no
  `description_en` column and no schema change.
